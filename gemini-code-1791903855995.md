# Portfolio Design Upgrade Plan

## 1. Purpose
Upgrade the existing portfolio into a polished, interactive engineering portfolio with an **Interactive Tech** visual direction.

The portfolio must present **Backend Engineering** and **Web3 Development** with equal prominence while preserving verified project facts, existing functionality, accessibility, and the current technology stack.

This document defines the proposed design upgrade track **D1–D6**. It does not override `AGENTS.md`, `PROJECT_PLAN.md`, or the project's approval requirements.

---

## 2. Authority and Execution Rules
Before any work, read:
1. `AGENTS.md`
2. `PROJECT_PLAN.md`
3. `PROGRESS.md`
4. This document

Follow the project's documented authority hierarchy. Higher-priority instructions always win.

### Mandatory Rules:
* **Execute one approved phase at a time.**
* **Do not start implementation** of a phase until the owner explicitly approves that specific phase.
* Approval of this overall plan **does not authorize implementation**.
* Before each phase, inspect relevant files and report the proposed scope, exact affected files, risks, and acceptance criteria.
* Stop and wait for approval when required by project rules.
* After implementation, run the applicable checks and report actual results.
* Do not mark work complete or approved without evidence and the required owner approval.
* Preserve all existing staged, unstaged, and untracked work.
* Never discard or overwrite existing work to make implementation easier.
* **Never run Git staging, unstaging, reset, restore, stash, or commit operations** unless separately and explicitly authorized.
* Do not modify `AGENTS.md` or `PROJECT_PLAN.md` without explicit owner approval.
* Do not introduce dependencies, frameworks, libraries, or external runtime requests without explicit approval.
* Do not invent project facts, skills, accomplishments, screenshots, or functionality.
* Do not infer file paths or project structure; inspect and verify them first.

> **Note:** If a rule conflict exists, stop and report it immediately.

## 3. Technology Constraints
### Current Intended Stack:
* **React**
* **Vite**
* **JSX**
* **Vanilla CSS**
* Standard React hooks and browser capabilities

### Restrictions:
* Do **NOT** introduce Tailwind, Bootstrap, animation libraries, icon libraries, UI component libraries, CSS-in-JS, or 3D/canvas engines without explicit approval.
* **No external runtime dependencies** such as CDN-hosted fonts, analytics, or remotely loaded interface assets.
* Use the existing design system and project conventions where practical. Confirm actual files before planning changes.

---

## 4. Visual Direction
**Design Concept:** Interactive Tech — restrained, precise, and engineering-focused.

### Desired Characteristics:
* Deep charcoal backgrounds with layered surfaces.
* Existing lime-green accent retained and used purposefully.
* Crisp technical borders and restrained highlights.
* Clear typography hierarchy using locally available system fonts.
* Monospace typography for terminal content, technical metadata, and section indices.
* Strong visual hierarchy and generous, consistent spacing.
* A full-screen, visually compelling hero section.
* Real project imagery where available and verified.
* Self-authored SVG/CSS or explicitly approved generated decorative visuals.
* Subtle, purposeful interactions rather than excessive animation.

> **Avoid:** Visual clutter, meaningless decorative controls, fake technical readouts, arbitrary proficiency percentages, and generic placeholder project images.

---

## 5. Design Upgrade Phases

### D1 — Visual Direction and Design System
**Objective:** Establish the visual foundation before adding new interactive features.

#### Potential Scope:
* Review and refine design tokens.
* Define background and surface elevation levels.
* Define borders, accent colors, typography, spacing, and transition tokens.
* Refine shared CSS primitives and background treatment.
* Establish consistent focus, hover, and active-state styling.
* Check color contrast for proposed text and interface colors.

*Expected files must be verified before approval. Candidate files may include:*
* `src/styles/tokens.css`
* `src/styles/base.css`
* `src/styles/components.css`
* `PROGRESS.md` (if project rules permit the proposed update)

*(Do not assume `tokens.css` exists prior to verification).*

#### Out of Scope:
* Changing JSX structure.
* Building the terminal.
* Rebuilding project cards.
* Implementing blockchain animations.
* Building the skills explorer.
* Adding animation libraries.

#### Acceptance Criteria:
* Existing sections continue to render.
* No project facts or existing behavior are unintentionally changed.
* Lint and build results are reported accurately.
* Relevant responsive layouts are checked.
* Proposed text and UI color combinations meet applicable contrast requirements.
* Reduced-motion behavior is considered from the beginning.
* All required phase checks and approval gates are satisfied.

---

### D2 — Full-Screen Hero and Functional Terminal
**Objective:** Make the hero more immersive and introduce a purposeful interactive terminal.

#### Potential Terminal Commands:
* `help`
* `skills`
* `projects`
* `contact`
* `clear`

#### Requirements:
* Commands must have genuine, understandable behavior.
* Output must be based on verified portfolio information.
* The terminal must not pretend to execute arbitrary operating-system commands.
* Keyboard interaction, focus handling, mobile usability, and accessible alternatives must be considered.
* Terminal output must remain truthful and must not invent capabilities or achievements.
* Follow the existing rule against fake terminals with no real purpose.

---

### D3 — Visual Project Showcase
**Objective:** Turn project presentation into a more visual and engaging experience.

#### Requirements:
* Preserve accurate project names, descriptions, status, and technology details.
* Use actual screenshots supplied or explicitly confirmed by the owner.
* Never present generated or placeholder images as screenshots of real projects.
* If screenshots are unavailable, design a truthful layout that can accommodate them later.
* Ensure project cards and interactions work on mobile and with a keyboard.
* *Potential scope includes project data, project components, styles, and approved image assets. Determine exact paths before implementation.*

---

### D4 — Blockchain Network Visualization
**Objective:** Add a restrained visual representation of blockchain nodes and connections.

#### Requirements:
* Prefer self-authored SVG or CSS.
* No additional dependencies without explicit approval.
* The graphic must not imply real-time blockchain activity unless it actually retrieves and verifies live data.
* Avoid unnecessary continuous animation.
* Support reduced-motion preferences.
* Keep the visual secondary to the portfolio's actual content.

---

### D5 — Interactive Skills Explorer
**Objective:** Make skills more engaging to explore without overstating expertise.

#### Preserve Current Positioning:
1. **Backend Engineering**
2. **Web3 Development**
3. **Data Analysis** (as a supporting capability)

#### Requirements:
* Do **NOT** invent proficiency percentages, skill levels, years of experience, or certifications.
* Interactive controls must perform a real function.
* Preserve clear content access without requiring hover.
* Support keyboard navigation and mobile layouts.
* Keep content understandable if interaction or animation is unavailable.

---

### D6 — Motion and Interaction Polish
**Objective:** Refine transitions and interactions after the main components are implemented.

#### Potential Scope:
* Consistent transition timing and easing.
* Focus, hover, pressed, and active states.
* Appropriate entrance or reveal effects.
* Motion coordination between sections.
* Performance and responsive checks.

#### Requirements:
* Honor `prefers-reduced-motion: reduce`.
* Avoid excessive movement, distracting loops, and unnecessary delays.
* Do not introduce an animation dependency without approval.
* **Do not begin D6 until D5 has passed its required checks and has been approved.**

---

## 6. Accessibility and Quality
Accessibility is a cross-cutting requirement throughout **D1–D6**, not a task to postpone until the end.

### Key Considerations:
* Semantic HTML and heading hierarchy.
* Keyboard access and visible focus.
* Text and non-text contrast.
* Descriptive links and controls.
* Appropriate alternative text for meaningful images.
* Responsive reflow and zoom.
* Reduced-motion preferences.
* Accessible feedback for interactive elements.

> **Note:** The formal accessibility phase remains governed by `PROJECT_PLAN.md` and `PROGRESS.md`. This document does not authorize reordering official project phases.

## 7. Phase Approval Workflow
For every design phase:
1. Read the governing project instructions and current progress.
2. Inspect the actual implementation and Git status.
3. Present the phase objective, scope, exact files, dependencies, risks, and acceptance criteria.
4. **Wait for explicit owner approval.**
5. Implement only the approved phase.
6. Run relevant lint, build, functional, accessibility, and responsive checks.
7. Report modified files, test evidence, limitations, and unresolved issues.
8. Update progress documentation only when permitted by project rules.
9. **Wait for explicit owner approval before starting the next phase.**

> **Constraint:** Do not combine multiple phases into one implementation.
